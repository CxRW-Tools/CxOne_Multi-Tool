Key properties
Self-updating
When the agent adds a capability or fixes a bug during your session, it repackages and exports an updated .skill file. Reinstall once to make the change permanent — improvements carry forward automatically.
Extensible by design
Ships with a comprehensive Checkmarx One OpenAPI spec and a module pattern guide. If you ask for something not yet built — a new report, a new SCM integration, a policy workflow — the agent looks it up and implements it on the spot.
Safe by default
Every bulk or destructive operation previews its planned actions before executing. Fuzzy quantities like "a bunch" or "most" are mapped to concrete values, stated out loud, and confirmed before proceeding.
One tenant at a time
Credentials live in a file in your own project folder, never the tool's shared temp location — so each project stays pointed at its own tenant. Work one tenant at a time; every command states which one it's acting on so a mismatch is easy to catch.
Runs as a container or a process
Long-running activity can run in a container so it keeps going when your laptop sleeps, or as a normal process if you have no container runtime.
Outage-safe cadence
If the host is down, missed events are dropped, never replayed — an outage becomes a realistic quiet gap instead of a late burst. A private ledger keeps per-project spacing consistent across restarts.
Tips for getting the most out of it
1
Just describe what you want. No commands or syntax needed — treat it like a conversation with a colleague who has full API access.
2
Vague quantities are fine. "A few", "some", "a bunch", "most" all translate to reasonable values. The agent states the value it chose before acting.
3
Dry-runs happen automatically before bulk or destructive actions. You'll see exactly what will change before anything is committed.
4
Ask for status anytime. "What's already configured?" or "Are the scans done?" — the agent queries live state rather than relying on memory.
5
Chain requests naturally. "Create a project, onboard this repo, set the preset to ASA Premium, and kick off a scan" works as a single message.
6
The API key is a refresh token — the agent reads your tenant and region from it automatically. No need to look up base URLs or tenant names.
⚠
Heads up on approval prompts. Every action the agent takes requires a click-to-approve in the Claude interface — a Claude permission model constraint. The tool batches common flows (one-shot project create, multi-repo onboard, quickstart) to minimize necessary approvals. Click "Allow for this session" on the first prompt to reduce friction further — but see "Working safely" below before bypassing approvals more broadly.
Three kinds of triage — pick deliberately
"Triage" can mean three very different things here. One invents results to make a demo look lived-in, one is a genuine security review, and one calls Checkmarx's own AI. Each has a different cost. Just say which outcome you want in plain English — the assistant will confirm which one it is before touching anything.
Simulated
Nobody reviews · invented
Weighted rolls pick a state and a canned comment, tuned to look like a real team's backlog — some projects well-kept, some neglected, a realistic untriaged tail. Perfect for filling a demo tenant. The verdicts are not real.
Free
Real review
The assistant reviews · genuine
Downloads the exact source the scan ran against, reads the vulnerable code and data flow, and writes a real verdict with a real comment citing the specific lines. If the code can't be read, it says so and triages nothing.

Checkmarx Assist
Checkmarx's AI agent · genuine
The platform's own agentic triage for SAST and SCA findings: reachability, exploitability and attackability with a confidence score and reasoning trace. Remediation Assist goes further and writes the fix.
Uses Checkmarx AI credits
Say it however you like. "Make this look lived-in" → simulated. "Actually review these four and triage them properly" → real review. "Run AI triage on the SQL injection" → Checkmarx Assist. If it's ambiguous, you'll be asked rather than guessed at — and anything that spends credits shows you the balance and the cost first.

Working safely — the one-tenant model
This tool acts directly on a live Checkmarx One tenant — creating, changing, and deleting real objects with an admin-scoped key. That power is the point, but it means the single most important habit is knowing which tenant you're pointed at before anything runs. The tool ships with a deliberate rule: work with exactly one tenant at a time. Follow the steps below and cross-tenant mistakes become very hard to make.
Confirm the active tenant before you act
Every command the agent runs opens with a standard line naming the tenant it's about to touch:
Active tenant: se_demo
Read it every time. If it isn't the tenant you mean to work on, stop — don't run the action. The agent can tell you which tenant is configured, but it can't know which one you intended; that check is yours.
One tenant per session — finish before you switch
Configure the one tenant you intend to work on and stay on it for the whole session. Don't run two chats against two different tenants at the same time, and don't switch tenants mid-task. To move to a different tenant, wrap up the current work first, then reconfigure (or start a fresh session). This is a working practice, not a lock the software enforces — so it depends on you keeping to it.
Let the dry-run and confirmation do their job
For anything that creates, changes, or deletes tenant state, the agent previews first: it dry-runs the action, lists the specific objects that will be affected — by name and count, e.g. "delete 3 projects: WebGoat, juice-shop, DVWA" — and waits for your explicit "yes." Read that list against the active tenant before you approve. It's your last, clearest chance to catch a wrong-tenant or wrong-scope action.
Keep credentials where they belong
Credentials are written to a file in your own working directory (e.g. cxone.env), never into the skill's temporary folder — which can be shared across sessions and wiped between them. Point each session at its own project file. Treat the API key as a secret even for demo tenants: don't paste it into chat repeatedly, and rotate it if it's ever exposed.
Be cautious with session-wide approval bypass
The Claude interface lets you approve an action once for the rest of the session (e.g. "Allow for this session"), and some setups let you bypass per-action approval entirely. That's a real convenience — it's possible — but it removes your last checkpoint before a live tenant change: the dry-run still runs, but nothing stops afterward to wait for your "yes." On a tool that can create, modify, and delete real tenant objects with an admin-scoped key, that's a meaningful risk to accept knowingly, not a default to reach for. Prefer approving per action, especially for anything destructive or bulk.
⚠
The tenant rule is a practice, not a guardrail. The tool detects and announces the active tenant and always previews destructive work — but it cannot technically prevent you from acting on the wrong tenant if you approve it anyway. Safety comes from reading the Active tenant: line and the previewed action list every time. When in doubt, ask "which tenant am I on?" before proceeding.
